# Plan the Fable design successor

## Decision

Record the user's selected Fable successor as the accepted planning direction
under the current request and standing authorization to accept Decisions: add
positive subject-specific design guidance, two directly routed modules,
proportionate records, a smaller three-operation Core, explicit optional
coordination, simplified draft metadata and measured local validation.
Use a new successor-v2 package contract for the changed module/status schema.
The user's current request authorizes planning and Fable plan acceptance, not
implementation, installation or publication. Final reviewer acceptance is not
proof that implementation or qualification has occurred.

## Problem

The independent Fable review and concrete follow-up propose a material change
to the content emphasis and runtime architecture. Current tools encode 28
successor-v1 modules and historical status names. Applying the new instructions
without coordinating registry, generator, validators and evidence would leave
an inconsistent package or rewrite the meaning of old tests.

## Drivers

- User-selected Fable proposals, preserved verbatim in the evaluation record.
- Positive practical design assistance, not only governance or negative rules.
- Standing advisory-budget rule ADR-0032 and unrestricted necessary expertise.
- Preserved design authority, protected content, legitimate conventional work,
  evidence limits and immutable prior qualification records.
- Plan-only scope now; focused implementation and validation later.

## Considered alternatives

- Retain the current package and perform only empirical evaluation. Lower
  structural cost, but does not implement the direction the user selected.
- Apply every proposed sentence literally. Simple transcription, but would
  reintroduce resource gates and can turn illustrative heuristics into universal
  requirements. Preserve Fable's mechanisms under the user's standing limits.
- Selected: implement the complete proposal map with explicit scope and evidence
  boundaries, versioned tooling and focused before/after verification.

## Consequences

The planned runtime has 30 directly indexed modules: the existing 28 plus
Generic Signatures and optional Sibling Coordination. Existing specialist
ownership and flat loading remain. Runtime status becomes draft without
erasing former labels or claiming improved qualification. Historical legacy-rc7
and successor-v1 packages remain testable under their original schema meaning.
The source and distributable manifest may differ only by the documented build
transformation removing the generator comment; both hashes are retained.

## Confirmation

Fable reviews the complete plan in the retained session. Later implementation
passes current-schema structure, legacy non-regression, changed routing and
real task evidence before a local candidate is handed off. No blanket efficacy
claim follows from model agreement or finite development cases.

## Revisit when

Fable identifies a material omission or contradiction, a new module cannot
route independently, a local rule loses a required safety/authority boundary,
or focused execution shows scope growth or design regression.
