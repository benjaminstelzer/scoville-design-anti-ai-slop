### Source headers and evidence meaning

Before W-001 package validation, every new or changed header uses actual
registered source IDs. Local authored heuristics use
`Sources: SRC-PACKAGE-LOCAL-SYNTHESIS` alone or alongside genuinely supporting
families. Provision that source-index entry with `Class: local-synthesis`,
authorship/version date, scope and limits; it explicitly denotes this package's
own heuristic, not an external publication or empirical proof. The v2 validator
accepts it only when that entry exists and preserves all normal source-ID
resolution checks. W-001 establishes the mapping; W-003 audits its substance and
disputed dates. No new header waits until W-003 to become structurally valid.

Core's status legend states: draft is development status; an empty evidence list
means no executed package-specific case receipt is attached. Planned fixture
IDs never count as evidence. After W-004 execution, each relevant module may
reference observed case receipts, including failures or limited/unverified
results, not only favorable cases. The repository receipt resolves the ID to
model/settings, case version, actual outcome, artifacts and tested package hash.
An evidence reference alone means neither passed nor generally qualified.
If annotation changes only evidence fields after a run, retain the tested
manifest and compare the annotated final manifest separately; verify that no
instruction, route, status or other behavior-affecting field changed. Do not
pretend the newly annotated hash was the tested one or repeat visual cases for
an explicitly verified metadata-only annotation.

7. Read-only critique of a supplied generic artifact containing both an actual

   no false defect for the valid pattern, minimal relevant findings and no
   artifact mutation. Preserve before/after source hashes and compare judgments

Use the same requested Fable 5.1 / High settings for before/after generation
where the execution harness supports the real task. The read-only consultation

mark that case unexecuted; do not substitute an imagined artifact or a prose

actual loaded modules, record burden and subject-specific design improvement.
For paired artifact judgment use a separate fresh reviewer with anonymized arm

mechanism needs an applicable inspected artifact. Extend the small set only if
that coverage mapping leaves a concrete gap. Do not trade away required proof
to meet an arbitrary case count. Preserve unfavorable valid outcomes and failed
attempts; after a real correction rerun only affected cases, labeled as a new
version rather than overwriting the earlier result.

Acceptance requires no unresolved introduced violation of content, authority,
scope or preserved strengths, plus observed improvement in the targeted generic
artifact dimensions. A legitimate conventional case must not be worsened merely
to raise specificity. Missing proof and material disagreement remain open, not
averaged into a green score. Finite development cases support only their tested
conditions, never a general superiority or release-readiness claim.

Host activation is a separate check: design-positive, pure backend/prose-negative,
strict incumbent implementation-negative and read-only critique prompts in a
real Skill-capable host. Testing already interpreted signals is not proof of

host configuration or report that lane unavailable. An unavailable host lane
