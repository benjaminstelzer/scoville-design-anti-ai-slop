# Per-reference expert-depth audit method

Date: 2026-09-02  
Status: W-011 research contract

## Scope

Audit every Markdown file in `references/` independently before changing the
executable package. Each audit must inspect the current file, the Core router,
its `modules.yaml` entry, source ledger, rule-to-source map, relevant evaluation
evidence, specialist public Skills, and authoritative learning or technical
sources.

Apply `docs/research/canonical-curriculum-method.md` across the full audit set.
Standard works, public lectures, design-school syllabi, OER courses, and
professional manuals supplement the per-reference web research. Copyrighted
works remain reference-only unless an explicit license permits adaptation.

The audit is about applied professional capability, not topic-name coverage.
It must distinguish knowledge already reliably supplied by Terra High from
instructions the Skill must focus, correct, teach, or externally verify.

## Required sections per reference

1. **Current contract**
   - activation signals, owned concerns, status, intervention class, sources,
     SOL/Terra evidence, token size;
   - explicit generation, critique, repair, exception, and verification rules.
2. **What is already strong**
   - rules that are specific, causal, source-bounded, and directly applicable.
3. **Missing professional capability**
   - missing variables, diagnostics, causes, decisions, repair techniques,
     medium/script/context distinctions, production checks, and escalation.
4. **Rule-quality audit**
   - binding constraints;
   - evidence-bounded rules;
   - contextual conventions;
   - heuristics or numeric starting points;
   - preferences;
   - justified exceptions and compensating structure;
   - slogans, cargo-cult numbers, or unsupported universals to reject.
5. **Specialist Skill prior art**
   - search GitHub and public Skill registries for Skills focused on this exact
     domain;
   - record repository, pinned commit or inspection date, license, mechanism
     worth learning from, and what must not be copied or generalized;
   - absence of a credible specialist Skill must be stated, not filled with a
     broad UI Skill.
6. **Authoritative research and learning sources**
   - prefer primary standards, official technical documentation, open books,
     peer-reviewed research, professional bodies, and practitioner material
     with explicit reuse status;
   - record source, version/date, license/status, claim supported, limit, and
     whether it may inform original synthesis or only be referenced.
   - include canonical books, lectures, courses, and recurring syllabus items
     relevant to the exact reference; do not assume popularity equals
     canonicality or public access equals reuse permission.
7. **Applied Dos and Don’ts**
   - concise actions that change generation, discrimination, critique, repair,
     or proof;
   - each consequential cluster has a source ID or bounded empirical rationale;
   - no live link is required for normal application.
8. **Architecture recommendation**
   - retain one leaf;
   - deepen to the smallest professionally sufficient payload;
   - split into named directly routed flat leaves;
   - keep only a bounded stub;
   - withhold until evidence exists.

The current 1,800-token ordinary-leaf figure is a cost target, not a quality
ceiling. Exceed it when an inseparable concern needs more applied instruction.
Split only when task signals can select the parts independently without losing
shared causal reasoning. Record measured leaf size, expected load frequency,
common multi-leaf combinations, and the smallest tested non-inferior payload.

For composition, typography, colour, imagery, UI, and production, explicitly
evaluate the medium architecture in
`docs/research/medium-architecture-question.md`: shared foundations versus a
responsive-web leaf, a print/fixed-media leaf, editorial/multi-page depth, or
medium branches inside the existing domains. Do not duplicate full domain
curricula merely to separate media.

Priority order is fixed: exact professional coverage and correctness first,
selective routing second, compression third. A smaller payload loses whenever
it omits a material criterion, exception, repair mechanism, ownership boundary,
or proof requirement.
9. **Tests and claim ceiling**
   - smallest open Terra High generation, critique, and repair cases that could
     falsify the proposed change;
   - deterministic checks, required render or production evidence, human or
     domain authority, and claims the tests still cannot support.
10. **Priority**
    - `P0`: current guidance can cause material falsehood, rights/access harm,
      destructive production error, or ownership failure;
    - `P1`: missing applied capability blocks the all-round designer goal;
    - `P2`: useful depth or efficiency improvement;
    - `P3`: history or enrichment with no current outcome gap.

## Evidence boundary

- A source list is not a rule set.
- One successful model output is not professional coverage.
- Public availability is not an open reuse license.
- A before/after example is not universal Gold.
- A numeric convention is never a universal law without population, language
  or script, medium, task, source, and override evidence.
- Token pressure may remove repetition, history, or model-prior exposition; it
  may not remove necessary professional criteria, binding floors, causal repair,
  or verification.
- Rules remain breakable when intent is declared, functional floors survive,
  compensating structure exists, and the whole result improves.
- No executable reference, `SKILL.md`, `modules.yaml`, benchmark Gold, or
  sealed holdout content changes during W-011.

## Stage two: top-three GitHub comparison

After all fourteen domain audits are complete, run a second current GitHub and
public-Skill search for every reference domain. Rank the three most-starred
qualifying repositories found on the capture date. Do not rank a repository
unless it contains a concrete Skill or directly usable agent instruction for
the exact concern and at least one inspectable evidence artifact.

Record for every candidate:

- repository and exact Skill path;
- current stars and capture timestamp;
- pinned commit, latest relevant update, and archived/active state;
- license for the exact Skill and any separate data/assets;
- claimed scope and actual mechanism;
- evidence level:
  - `E0`: prose claim only;
  - `E1`: inspectable examples or output artifacts;
  - `E2`: reproducible tests, evals, or deterministic checks;
  - `E3`: independent evaluation or external adoption evidence;
- whether the evidence shows routing, output completeness, functional
  correctness, visual quality, or only self-description;
- what the candidate does better than the current Scoville reference;
- mechanism to adopt or adapt through original synthesis;
- hardcoded recipe, unsafe ownership, unsupported claim, dependency, or
  licensing issue to reject.

Only `E1` or higher qualifies for the top-three comparison. Stars measure
popularity, not capability, so star rank and evidence rank remain separate.
When fewer than three credible exact-domain Skills exist, report the bounded
search and the shortfall rather than substituting a general UI or prompt
repository. Do not claim global exhaustiveness when GitHub search, API, or rate
limits prevent it.

Apply the weighted adoption questions in
`docs/research/adoption-priority.md`. Typography/typesetting, spacing/rhythm,
negative space, hierarchy, and subject-specific composition are the primary
comparison lens across all visual Skills. Require visible examples, tests, or
artifacts that support those claims; README terminology alone is not evidence.

The typography audit and comparison must also answer every question in
`docs/research/typography-rule-questions.md`, including source-backed general
principles for family compatibility and a scoped decision rule for how many
families a system should use. The serif/sans pattern is an example, not the
rule model.
